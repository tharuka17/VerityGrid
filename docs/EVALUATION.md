# VerityGrid evaluation

This file records the results of the evaluation, how to read them and how to reproduce them. The reports generated by the commands are authoritative; this document is a snapshot of them.

| Source of evidence | State |
|---|---|
| Deterministic detectors | **Run.** Results in [section 3](#3-deterministic-detectors). Reproducible. |
| Mock classification provider (a keyword placeholder, **not** an LLM) | **Run.** Results in [section 4](#4-mock-classification-provider). Reproducible. |
| A real language model (`gemini-3.5-flash-lite`) | **Run once**, on 2026-11-19. Results in [section 5](#5-the-real-language-model-one-run). A single, non-reproducible run. |
| Human review counts | Not part of this snapshot. The report can include them from a local database; they are not ground truth. |

**Provenance of the numbers.**
- *Reproducible parts (sections 3 and 4):* first generated 2026-11-14 at 09:55 UTC on the author's Windows machine (Python 3.14.2, pandas 3.0.6, 5 passes). The results fingerprint was identical on every later run, including after the later code changes: it is `67077ce4bc4e8fd3324cbf163f6be21aeb698feb21ae84c85117c50c63bd8d2e`, and the dataset fingerprint is `b8bfbe301c02…`. The test suite rebuilds the report on every run and fails if these numbers or the fingerprints move.
- *The real-model run (section 5):* one run on 2026-11-19, report time 14:21 UTC, same machine. It is not reproducible: no temperature is set, so a repeat may differ.

## 1. Reproduce it

The deterministic and mock parts need no server, no network and no key:

```powershell
python -m app.evaluation.harness --skip-review
```

It writes `reports/evaluation_report.json` and `reports/evaluation_report.md`, prints the fingerprints, and every run on the same code must print the same results fingerprint. The fingerprint covers the dataset, the deterministic metrics and the mock metrics. It excludes timings, timestamps, real-model output and review data. `python -m pytest tests/test_evaluation.py -q` runs the harness's own tests (they never use a real provider).

The real-model run needs a Gemini key and model in your local `.env` (`AI_PROVIDER=gemini`, `GEMINI_API_KEY`, `GEMINI_MODEL`) and makes real provider calls:

```powershell
python -m app.evaluation.llm_run --cases customers_clean
python -m app.evaluation.llm_run
```

The first line is a 7-column trial; the second is the full run. The command waits 6 seconds between calls by default, stops sending calls after 8 consecutive failures, asks for confirmation and writes to `reports/llm_trial` or `reports/llm_run`, never over the reproducible report. Its tests use fake providers only.

## 2. What is evaluated

A fixed, deterministic, **synthetic** dataset with hand-written labels:

| | |
|---|---|
| Cases | 13 (standard 8, near-miss 4, known-limitation 1) |
| Labelled columns | 63 (`internal` 35, `personal` 11, `financial` 7, `public` 5, `unknown` 5) |
| Rows | 132 |
| Detection units | 328 (a unit is one column and category pair, or one case and `duplicate_rows`) |
| Actual positives | 20 (`missing_values` 5, `potential_phone` 5, `potential_email` 4, `numeric_rule_violation` 2, `invalid_date` 2, `duplicate_rows` 2) |

Near-miss cases contain values that only look like a risk (phone- or email-shaped text that is not, rules that are not configured, rows that differ in one column). The known-limitation case contains risks the detectors are documented **not** to handle, so the report shows weaknesses instead of hiding them. A separate check re-derives the labels with simple independent tests, and the harness refuses to run on an inconsistent dataset. The harness runs the **real scan workflow** with each case's own rules, not a copy of its logic.

## 5. The real language model: one run

### 5.1 What was run

`gemini:gemini-3.5-flash-lite` classified every labelled column through the project's classifier on 2026-11-19, using the same sanitized metadata as always (an opaque column reference, the sanitized column name, inferred type, null and distinct shares and finding summaries; **never cell values**). Calls were paced 6 seconds apart with a stop rule of 8 consecutive failures (never triggered). The adapter allowed 2 attempts per call. This was **a single, non-reproducible run**: no temperature is set.

### 5.2 Result

| Source | Accuracy | 95% interval | Macro F1 | Columns answered |
|---|---|---|---|---|
| Always answering `internal` | 0.556 | n/a | n/a | n/a |
| Mock (keyword placeholder) | 0.698 | [0.58, 0.80] | 0.645 | 63 of 63 |
| Gemini 3.5 Flash-Lite | 0.794 | [0.68, 0.88] | 0.800 | 60 of 63 |

- **Accuracy counting the 3 unanswered columns as wrong: 0.794** (50 of 63). **Over the 60 answered columns only: 0.833** (50 of 60). The second figure leaves failures out and can flatter the model if the failures are not random; the first is the fair headline.
- Macro: precision 0.796, recall 0.845, F1 0.800. Micro: precision 0.833, recall 0.794, F1 0.813.
- Coverage: 60 of 63 columns received a valid answer.

### 5.4 Compared with the mock

0.794 is higher than 0.698, but **the two are not distinguishable on this dataset**: the intervals overlap ([0.68, 0.88] and [0.58, 0.80]). Comparing the two lists of wrong columns directly, which is the more sensitive comparison:

- wrong for both: 7
- wrong only for the mock: 12
- wrong only for the model: 6

An exact paired test (McNemar) on the 12 and 6 gives a two-sided p-value of about 0.24 (the author's calculation from the report). That is not evidence of a difference, and it flatters the model: the 63 columns are not independent (the same column name appears in several cases). The model's per-class advantage on `public` recall (0.600 against 0.200) and `personal` recall (0.909 against 0.727) rests on 5 and 11 columns.

### 5.5 What its errors look like

Of the 10 errors among the 60 answered columns:
- **8 label an internal column as `personal` (4) or `unknown` (4).** `customer_id`, `customer_ref` (twice) and `ten_digit_id` were called `personal`; `delivery_notes`, `meeting_note`, `placeholder_missing` and `blank_strings` were called `unknown`. Under the project's policy both labels force human review, so these cost reviewer time without hiding anything.
- **1 labels a public column `internal`** (`branch_name`).
- **1 labels an internal column `public`** (`release_version`). This is the only error that understates sensitivity.

No `personal` column was labelled as anything other than `personal`; the one unanswered personal column is `mobile_phone`. These observations come from 10 errors and say little about other data.

### 5.6 Failures and timing

Three columns got no answer: `store_hours` (`inventory_clean`), `mobile_phone` (`pii_patterns`) and `shipment_id` (`numeric_and_date_rules`). Two ended as `provider_unavailable` (HTTP 503 responses on both attempts) and one as `provider_error` (a read timeout at the adapter's 20-second limit; the adapter maps only HTTP statuses to "unavailable", so a timeout is recorded as an error). Other 503 and 504 responses were retried successfully. A rate limit was not the problem: pacing kept the run within the free tier's request limit.

Per-call latency, retries included: minimum 1.2 s, median 7.6 s, mean 7.8 s, maximum 40.7 s. With 372 s of pauses the run lasted roughly 14 minutes (derived from the report). Workflow latency in the model section includes the pauses.

### 5.7 Cost and data use

The harness does not measure cost or tokens. The provider's usage page showed roughly 80 requests, 30 thousand input tokens and 5 thousand output tokens for 2026-11-19, which includes the 7-column trial (approximate chart readings). On 2026-11-14 the project showed the Free tier badge and a prompt to set up billing, so no billing was linked then; the author has seen no evidence of a charge. On the free tier the provider may use content to improve its products (per the provider's pricing page); only sanitized column metadata of the synthetic dataset was sent.

### 5.8 What the Docker demo shows

The API image serves a **committed snapshot** of this run, `data/evaluation/llm_run_2026-11-19.json`, as its evaluation report, so the dashboard's Evaluation page shows the real-model section with its coverage and pacing. The image still runs the harness at build time as a self-check. A test keeps the snapshot honest: its deterministic and mock results and its fingerprints must equal what the code produces today, and its counts must be internally consistent. To refresh it, repeat the run, save the new report with a dated name, and update `Dockerfile.api`, the snapshot tests and the figures in this document; the tests name whatever disagrees.

## 6. How to read these numbers

- **Compare with the baseline and the mock.** An accuracy only means something if it clearly beats the alternatives; intervals that overlap do not.
- **Report failures with the result.** Rate limits and outages say nothing about a model's judgement, so coverage and answered-only accuracy are shown next to the main figure, with the caveat that failures need not be random.
- **Small supports make per-class rates unstable.** Five or seven columns per class is too few for firm statements.
- **The mock's `unknown` and `financial` figures are artefacts** of its fallback and of keyword-bearing column names written by the same author.
- **Three sources of evidence are never combined.** The harness raises an error if a classification carries the wrong provenance (`mock` versus `llm`).

## 7. Limitations of this evaluation

Small and imbalanced (63 labelled columns, 20 detection positives); synthetic; labels, detectors, mock and dataset written by the same author, with no independent annotator and no held-out set; **one** real-model run of one model, so a repeat may differ; no hostile column names, so behaviour under prompt injection is untested against a live model; three columns unanswered because of provider failures; cost and tokens not measured by the harness; timings are machine-dependent; the human-review section is optional and is not ground truth. The results describe how this implementation behaves on cases its author could anticipate. They do not estimate real-world performance.
