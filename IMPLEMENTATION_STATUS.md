## Environment

- Development uses Claude chat plus local VS Code.
- Files are created manually by copying code from chat.
- Commands and tests are run locally in Windows PowerShell; real output is reported back for debugging. Edits must be saved before tests are run (one 9B-2 run was made before saving and showed the old counts).
- Python 3.14.2, pandas 3.0.6 (both reported by the evaluation harness) and FastAPI 0.143.2 (reported by `pip show fastapi`) in a local `.venv` (the project's single consistent Python version). FastAPI 0.137.0 and later keep included routers as nested objects (`_IncludedRouter`) instead of copying their routes, so code and tests must not look for route paths in `app.routes`; use the OpenAPI document instead.
- Docker is installed on the developer's machine (`docker compose` with the current Compose syntax worked; the exact versions were not reported). The images are named `veritygrid-api` and `veritygrid-ui`; the official base image `python:3.14-slim` exists on Docker Hub (confirmed by search; the exact patch version used was not reported).
- The project folder is under OneDrive (`C:\Users\USER\OneDrive\Desktop\VerityGrid`); OneDrive syncing of the live SQLite file and `.venv` may cause locking or slowness.
- No repository has been initialized. Git and GitHub are introduced only on request.
- Running the dashboard needs two terminals at once (API: `uvicorn app.main:app --reload`; dashboard: `streamlit run ui/streamlit_app.py --browser.gatherUsageStats false`), each with the virtual environment activated; a third terminal is for one-off checks and tests. Commands must be pasted one at a time, not on one line. After saving a UI file, click Rerun in the browser (or press R); `uvicorn --reload` restarts the API when backend files change but not when `.env` changes. The API must be started from the project folder (the evaluation endpoint reads `reports/evaluation_report.json` relative to the working directory). The evaluation harness needs no server. The Docker demo uses ports 8000 and 8501 on `127.0.0.1`, so a local API or dashboard must be stopped first.
- Access mode (10A): the developer's `.env` contains `VERITYGRID_MODE=development` (so local writes work); the default when the variable is unset or invalid is `demo` (read-only). `$env:` variables set in one PowerShell terminal exist only in that terminal (a `Remove-Item Env:...` in a fresh terminal fails harmlessly with "does not exist"). The test suite runs in development mode through the project-root `conftest.py`. To run the read-only demo locally: `python -m scripts.seed_demo`, then in the API terminal set `$env:DATABASE_URL = "sqlite:///./veritygrid_demo.db"` and `$env:VERITYGRID_MODE = "demo"` and run `uvicorn app.main:app --reload`. Application INFO log lines (such as the demo-mode announcement) are not shown by uvicorn's default logging; the development-mode WARNING and the "Write request rejected" WARNING are.
- Pasted terminal output sometimes loses a space at a line wrap (seen as "notintentional" in Phase 8 and as "intervalsshow", "ofcases", "macroaverages", "runson" in the 9A report paste); the code strings contain the spaces, so these are presumed paste artifacts (not confirmed by opening the files).
- The Gemini project is named `VerityGrid` and is on the Free tier (Google AI Studio usage page, 28-day view, UTC-8). Token usage, request counts, errors and rate limits per model can be read there (the evaluation harness does not measure tokens or cost).

## Open decisions

- **Deferred to Phase 12-0 (developer's choice): detection configuration over HTTP.** `POST /scans` always runs the detectors with the default `DetectionConfig`, so numeric-range rules and date-validity rules cannot be activated through the API (or the dashboard). Consequently the sample inventory's negative quantity (`-12`) and impossible date (`2026-02-30`) are never reported over HTTP, although the detector tests prove the rules work and the evaluation harness exercises them by passing explicit rules per case (the `numeric_and_date_rules` case; the `unconfigured_rules` case checks that nothing is reported when no rule is configured). The project brief lists configurable numeric and date rules in the MVP. Options: an optional validated rules field on the upload; rules stored per dataset (adds a table, so a one-time database reset); or built-in presets for the sample datasets. Any option is additive and does not break existing API calls. The Upload view and the Findings explorer tell users that these rules are not active, and the README lists it as a limitation. Until it is settled, any demo should say the same.
- **Deferred to Phase 12-0 (developer's choice): `PROJECT_SPEC.md` revision.** The spec still describes the original plan and must be updated to record the items listed below. A reviewer who opens the old spec would see the original plan, so revise it (or put a "historical plan" banner at its top) before the repository is published. - Phase 7B design decisions to record in the spec:
  - `run_scan(db, df, *, dataset_name, source_filename=None, config=None, classifier=None) -> ScanResult`. The compute step is `run_scan_workflow(df, dataset_name=..., options=WorkflowOptions(classify=classifier is not None, detection_config=config), classifier=classifier)`. Default workflow caps apply (50 columns, breaker at 3 consecutive failures); they are not tunable through `run_scan` yet. The three-transaction structure, input validation, result shape (`ScanResult` unchanged) and failure messages are preserved.
  - A `failed` workflow result raises an internal `_WorkflowFailed` carrying a reason only and flows through the existing failure path: rollback, `ScanRun` marked `failed` with a generic reason, and `ScanFailedError`. A partially completed workflow persists its valid deterministic results and any classifications that succeeded; `ScanRun.status` stays `completed` because the status set has no partial value.
  - `ScanRun.summary` keeps its five existing keys. A `workflow` block (`status`, `steps`, `classification` counts and provider name, `risk` counts, `issues`, `durations_ms`) is added only when classification was requested or the workflow did not complete cleanly. The block holds no column names or values.
  - Classification is stored on `ColumnProfile` using the existing columns: not attempted: all three NULL; attempted and failed: label NULL, source `none`, explanation = the generic fallback text; succeeded: validated label, source `mock` or `llm`, explanation.
  - Provider calls happen in the compute step, outside any open database transaction. If persistence then fails, the calls have already happened but nothing from them is kept (pinned by a test).
  - Three existing tests were patched to inject detector failures at `scan_graph.run_detectors` instead of `scan_service.run_detectors`; their assertions are unchanged.
- Phase 7A design decisions to record in the spec:
  - Workflow `app/workflows/scan_graph.py`: `run_scan_workflow(df, *, dataset_name, options=None, classifier=None) -> WorkflowResult`; `build_scan_graph(df, *, options, classifier)`; `WorkflowOptions` (`classify` default False, `max_classified_columns` default 50 in 1–200, `max_consecutive_failures` default 3 in 1–10, `detection_config`).
  - Steps: `validate_input`, `profile_dataset`, `run_checks`, `classify_columns` (only when requested), `consolidate`, `apply_policy`, `finalize`. The graph is acyclic; `RECURSION_LIMIT` is 20 as a backstop. Node names differ from state keys.
  - Existing services are reused unchanged; the workflow reimplements none of their logic. The classifier is injected explicitly; the workflow never builds a provider or reads settings.
  - The DataFrame is not in graph state (closures only). State is typed (`ScanState`), with `operator.add` reducers for steps, issues and timings.
  - Failure semantics: `validate_input`, `profile_dataset`, `run_checks` and `finalize` are fatal (status `failed`); `classify_columns`, `consolidate` and `apply_policy` are non-fatal (status `partially_completed`, deterministic results kept). Issues hold a step, a stable code and an exception class name; never messages, values or column names. Wrong argument types and `classify=True` without a classifier raise `TypeError` or `ValueError`.
  - Cost and retries: classification is off by default; one provider call per classified column; the cap and a circuit breaker bound calls. The workflow adds no retries of its own (the provider owns bounded retries). The compute phase has no side effects, so whole-workflow re-runs are safe.
  - Policy (`assess_column`): column risk is the highest finding severity (low if none), raised to at least medium by a usable `personal` or `financial` suggestion; a column needs review when it has a HIGH finding, an email or phone finding, or a usable suggestion whose recommendation is `review_required`. Dataset risk is the highest of all finding severities and column risks. AI output can raise attention but never lowers what findings established. The workflow never sets a review status; humans decide in the review API.
  - Result: `WorkflowResult` with `to_summary()` returning counts, statuses, step names, issue codes and timings only.

  - Developer-specified labels: `public`, `internal`, `personal`, `financial`, `unknown`. Review recommendation values: `review_required`, `review_recommended`, `review_optional`. Source values: `mock`, `llm`, `none` (`none` marks a fallback result).
  - Interface: `ClassificationProvider` (abstract; class attributes `name` and `source`; `classify(ColumnMetadata) -> Mapping`), `ProviderUnavailableError`. The provider returns a raw mapping, validated by the classifier against `ClassificationSuggestion` (unknown fields rejected so a provider cannot assert its own provenance).
  - Provider input (`ColumnMetadata`): opaque `column_ref` (`col_N`), sanitized column name (NFKC, control and invisible characters removed, whitespace collapsed, at most 64 characters), inferred type, row count, null percent, distinct percent of non-null values, and per-column finding summaries (category, severity, safe scalar evidence only). Finding titles and descriptions are not sent; dataset-level findings are not sent.
  - Output rules: explanation at most 300 characters, no control characters; at most 8 supporting references, each of a fixed shape and each one offered in the request, otherwise the output is rejected.
  - `ColumnClassifier` (no database access): builds metadata, calls the provider, validates, applies policy and returns `ClassificationResult`. Provenance is set by the classifier. Failures never raise: they become a fallback result (label `unknown`, `review_required`, source `none`, fixed generic explanation, no references).

  - Endpoints and status codes: `POST /scans` 201 (413 too large, 422 invalid, 500 scan failed); `GET /scans/{id}`, `GET /datasets`, `GET /datasets/{id}`, `GET /datasets/{id}/columns`, `GET /findings`, `GET /findings/{id}`, `GET /metrics/summary` 200 (and, from Phase 9B, `GET /evaluation/report` 200); `POST /findings/{id}/review` 201; 404 for missing records; 422 for validation errors, including ids outside 1 to 2,147,483,647; in demo mode (10A) every non-GET, HEAD or OPTIONS request is 403 `read_only_mode`.

Findings are ordered by severity (HIGH first) then id; datasets newest first; column profiles not paginated (at most 200).

## Design notes not covered elsewhere

The decisions behind the architecture are in `PROJECT_SPEC.md` (sections 12 and 14), `docs/ARCHITECTURE.md` and `SECURITY.md`. Smaller choices:

- **Dashboard:** every failure becomes an `ApiError` of kind `unreachable`, `timeout`, `http_error` or `invalid_response`; views show an explanation and never placeholder numbers. Cached reads last 5 seconds (health) or 10 seconds; "Refresh data" clears the cache and writes clear it too. Untrusted text is shown with `st.text` or inside tables, never as markup (a static test enforces it). The Findings explorer's "Review this finding" button hands a finding id to the Review queue through `st.session_state["review_selected_finding"]`. The dashboard settings read only `VERITYGRID_*` variables.
- **Scan service:** three transactions (create; persist everything and mark completed once; on failure roll back and mark failed). A partly completed workflow persists its deterministic results and keeps the scan status `completed`, with a workflow block in the summary. Classification is stored in the existing `ColumnProfile` columns.
- **Review:** one commit writes the decision, the status and the audit event; the status always equals the latest decision; audit metadata never holds the comment.
- **Evaluation:** a rate with a zero denominator is `None` and shown as `n/a`; macro averages cover only classes with examples; every false positive and false negative is listed; the harness refuses to run on an inconsistent dataset and raises if a classification carries the wrong provenance; the results fingerprint excludes timings, timestamps, real-model output and review data.
- **Errors:** one shape `{"error": {"code", "message", "issues"?}}`; a request-validation error carries a location and a rule text, never the submitted value; the 500 handler is generic.
- **Rules:** validated by `app/schemas/rules.py`; the route turns a rejection into the shared 422 with the location `body.rules...`; the dashboard only displays the API's answer and keeps one drift-tested copy of the 20,000-character limit.
  - Integer auto-increment primary keys.
  - Allowed values: scan status (`pending`, `running`, `completed`, `failed`), severity (`low`, `medium`, `high`), review status/decision (`pending`, `approved`, `rejected`), stored as plain strings with validation in Pydantic schemas.
  - JSON columns: `ScanRun.summary`, `Finding.safe_evidence`, `AuditEvent.safe_metadata`.
  - `AuditEvent` references entities loosely (no foreign key). Cascade deletes exist for dependent rows; the application never deletes records automatically.
- `DATABASE_URL` defaults to `sqlite:///./veritygrid.db`. A PostgreSQL driver and URL form are decided only when PostgreSQL is actually targeted; no migrations tooling is used (`create_all` only).
